# 附录 C　术语表

## C.1 判据：为什么有些词不翻译

本书对术语只遵循一条判据：

> **这个英文词，在中文技术语境里有没有一个稳定、无歧义的译法？**<br>
> 有 → 用中文。没有，或译了会让人误解 → **保留英文原词**，并在首次出现处用一句白话解释。

按这条判据，需要单独说明的只有三类：

### 保留英文的词

| 保留 | 常见中译 | 为什么不译 |
|---|---|---|
| **token** | 词元 / 令牌 | "令牌"已被"认证令牌""硬件令牌"占用——说"写一页代码要花掉几万个令牌"会让人跳到密码和密钥上去。"词元"虽准确，但没人真的这么说 |
| **harness** | 线束 / 挽具 | 中文里没有稳定对应物；"线束"首先指汽车电缆总成。这是 2026 年才被命名的工程概念 |

### 译作"智能体"的词

| 词 | 本书用法 | 理由 |
|---|---|---|
| **agent** | **智能体** | 这是本书与 V2 最重要的一个变化。V2 保留英文，理由是这个译法"太宽"。该理由在写给工程师看时成立；但当读者里有一半不写代码时，**"智能体"才是那个不需要解释就能被理解的说法**——而且它已经是国家标准和政策文件的用词（如国发〔2025〕11号） |
| **agentic** | agentic（形容词） | 无稳定译法；"智能体化的"读起来别扭 |
| **agentic engineering** | 保留英文 | 一种工作方式的名称，2026 年由 Karpathy 提出 |

### 有稳定中文译法、直接用中文的词

> **判据对照**：`prompt` 与 `context` 也属于这一类——它们的中文译法已经稳定，所以本书**用中文**（"提示词""上下文工程"），不保留英文。列此仅为说明判据的一致性，不是例外。

sandbox→**沙箱** · routing→**路由** · benchmark→**基准** · spec→**规格** · diff→**变更** · checkpoint→**检查点** · trace→**追踪** · guardrail→**护栏** · prompt→**提示词** · context engineering→**上下文工程** · prompt injection→**提示注入** · retrieval→**检索** · embedding→**嵌入向量** · chunk→**分块** · observability→**可观测性** · artifact→**产物** · idempotency→**幂等** · evaluation→**评估** · walkthrough→**走读**

## C.2 本书的核心概念

| 概念 | 定义 | 出现位置 |
|---|---|---|
| **vibe coding** | 让 AI 写代码，**而你不审查它写出来的东西**。关键词是"不审查"，不是"用 AI" | 第 1 章 |
| **验证鸿沟** | 生成代码的速度与验证代码正确性的速度之间持续扩大的差距。**生成以秒计，验证以小时计** | 第 5 章 |
| **三种税** | **验证税**（刚性）、**认知税**（隐蔽）、**责任税**（最贵）。它们解释了为什么代码变便宜了、工程师反而变贵了 | 第 5 章 |
| **认知债** | 团队对系统的真实理解，与系统实际有多复杂之间，正在扩大的那道裂口。技术债是"代码不好但看得懂"，认知债是"**代码没问题但没人敢动**" | 第 10 章 |
| **锯齿边界** | 模型的能力边界不是平滑的线：有些难题它做得很漂亮，有些看起来简单的事它做不对，**且无法从难度预测** | 第 3 章 |
| **签名线** | 区分"可委托"与"不可委托"的分界。线的一侧：动作可被机器判定对错、后果可回滚或隔离；另一侧：需要理解、可追责主体与留痕 | 第 15 章 |
| **颅内沟通** | 当一个人就是一支队伍时，团队内部的所有沟通从"跨人传递"变成"颅内闭环"。它压缩的不是打字时间，是**协调时间** | 第 6 章 |
| **上下文焦虑** | 模型感知接近上下文上限时会**提前收尾**，把没干完的活包装成"已完成" | 第 2 章 |
| **自主性鸿沟** | 企业级 AI 使用中，绝大多数仍停留在"辅助"档，真正端到端自主的比例很小 | 第 14 章 |
| **幻觉** | 模型生成流利、自信但与事实不符的内容。**不是 bug，是"猜下一个词"机制的必然副产品** | 第 2 章 |
| **校准失效** | 幻觉里最危险的一类：对一个真实问题给出可信、完整、**错误的**答案。它能通过编译、测试与评审，直到某个边界条件被触发 | 第 2 章 |
| **治理下沉** | 约束载体沿"口头提醒 → 文档 → 检查清单 → 机器门禁"逐级下沉；**每下沉一级，违规成本从"靠自觉"变成"被阻断"** | 第 10 章 |
| **门禁** | 流程里那道"不满足就不许往下走"的闸口。**它管的是"能不能过"，不是"好不好"**——判断好坏是评审的事，判断能不能过是门禁的事 | 第 10 章 |
| **深模块** | 窄接口、厚实现——一行调用背后藏着上千行机制。**复杂度不会消失，只能被收纳，而收纳它的容器就是模块边界** | 第 10 章 |
| **AI 物料清单** | 记录模型版本、提示版本、依赖清单与审批记录，让 AI 产出可追溯 | 第 12 章 |
| **四拍** | 一个 AI 协作循环的四个拍子：**意图 → 生成 → 验证 → 判断**。第一拍的产出是共识而不是代码；四拍里最常被省掉的是第三拍，因为它最贵 | 第 8 章 |
| **评审流利度** | 读完一份几百行的生成变更，快速找出"哪几行会出事"的能力。**它和"会写"是两种能力**——你得先会写才知道该看哪里，但光会写不一定看得快 | 第 15 章 |
| **硅碳十律** | 作者在自己项目里沉淀的一套人机协作原则（碳基指人，硅基指 AI）：1 条公理 + 3 个层次 × 3 条，管"做正确的事、正确地做事、让方式持续进化" | 第 6 章 |

## C.3 容易混淆的几组词

| 容易混的两件事 | 区别 |
|---|---|
| **vibe coding** vs **AI 辅助的软件开发** | 前者不审查，后者审查。**判断标准不是你用没用 AI，是你能不能解释自己提交的那一行** |
| **提示词** vs **规格** | 区别不在长短，在**能不能被判定**。能被逐条验收的是规格 |
| **技术债** vs **认知债** | 技术债能估利息、能扫出来；认知债没有报表，唯一表现是"**这块没人敢碰**" |
| **验证** vs **校验** vs **评审** | **验证**=确认它符合预期（机器与人合作）；**校验**=机械地判定格式/规则；**评审**=人的判断，聚焦机器审不出的设计、边界与安全 |
| **生成者** vs **验证者** | **生成者不能认证自己的作品。**同一轮对话里的"我检查过了"，信息量接近零 |
| **模型** vs **harness** vs **智能体** | 模型是权重（发动机）；harness 是模型外面那一整套工程设施（整台车）；智能体是"模型 + harness"运行起来的样子 |
| **采纳率** vs **入库率** | 采纳率至少有四层含义；**只有"真实合入主干的量"那一层算数** |
| **目标值** vs **达成值** | **永远分列，不得并进同一格**——并格会凭空造出一条源材料里不存在的"合格线" |
| **测试通过** vs **安全** | 两件事。功能正确率可以一路升上去，安全失败率却可以多年持平（数据见附录 A 第 28 条） |
| **"能跑"** vs **"能做对"** | 一个跑得通但集成点错配的改动，和一个明显的 bug，是两种不同的危险 |

## C.4 本书的表述与体例约定

| 词 | 说明 |
|---|---|
| **V3 相对 V2 的术语调整** | 正文里的 **agent 一律改作"智能体"**（理由见 C.1）；`agent` 仅在代码、命令、协议名中保留原样 |
| **"签名的是人"** | 本书对责任归属的核心表述。**智能体可以做得比人快、也可以做得比人好，但它不能签名** |
| **"对不写代码的人意味着什么"** | 本书的体例积木之一：每章在"本章小结"之后，给非工程读者一个可以直接使用的落点 |
| **"一句话讲明白"** | 本书的体例积木之一：用日常语言解释一个术语或机制 |

# 第 2 章　从猜下一个词说起

**本章承诺**：读完这一章，你能从生成机制入手，理解模型的一些本领与局限——包括它为什么可能一本正经地编造、为什么同一个问题问两遍答案不一样、以及为什么"一次能读下整个仓库"却不等于可靠地用上每一段。

**读完后你能回答**

- 为什么它能把一个函数写得漂亮，却在两个函数的衔接处编出一个不存在的参数？
- 为什么同一个问题问两遍，答案会不一样？
- "上下文窗口大到能装下整个仓库"，为什么还不等于"它记住了整个仓库"？

---

## 2.1 一台"下一个词"的机器

理解大语言模型的文字生成，可以先记住一句话：

> **常见的自回归模型，会根据已有上下文预测下一个 token，再接着生成。**

先把 token 粗略当成"词"。你写"今天天气"，它算出后续各个 token 的概率，再按生成设置挑一个，接上去。再猜下一个。如此往复，直到输出结束标记或达到长度限制。

你看到的一气呵成的回答，就是这样一步步接出来的。**但输出流畅，不保证事实正确。**

这解释了文字怎样生成，却不能单凭它推出模型的全部能力与限制。**训练数据与方法、后训练、推理时投入的计算、可用上下文和工具，都会影响它能做好什么。**

- **它为什么懂那么多？** 训练让它从大量代码、文档、论坛问答、教科书、issue 讨论里学到知识与模式，后训练等环节也会影响它怎样运用这些能力。
- **它为什么可能不了解你的项目？** 因为项目事实未必在训练数据或当前上下文里。把相关代码、文档交给它，或让它用工具查，能补上信息，但仍要核验。
- **它为什么能写漂亮的函数、却在两个函数的衔接处编参数？** 因为符合常见写法，不等于符合你们系统的真实接口。缺少信息或推断出错时，它仍可能给出看起来顺畅的答案。

> **定义 · token**<br>
> 模型处理文字的基本单位。它先把文字切成一个个小块（可以是一个词块、半个词，也可以就是一个标点），每一块叫一个 token。具体怎么切，取决于模型使用的分词器。<br>
> 为什么要知道这个？因为**上下文与输出长度的上限通常用 token 计，许多服务也按 token 收费，但它不是全部成本和限制的唯一单位。**

还有一类推理模型，会在给出最终回答前投入额外的推理计算。**中间过程不一定完整展示给用户**，所以不能只凭最终回答，就判断它到底检查过什么。工程上仍要靠可见的工具调用、测试结果与留痕来核验，而不是把一段推理说明当成审计证据。

## 2.2 它为什么会一本正经地编

> **定义 · 幻觉（hallucination）**<br>
> 模型生成与事实不符或缺乏依据的内容，往往还说得流利、自信。**自回归生成本身不保证事实正确**；幻觉也受训练、上下文、推理与工具等因素影响，不能只归因于"猜下一个词"。

有个经典例子到今天仍值得警惕。你让模型读一个 YAML 配置文件，它可能会写出 `pd.read_yaml(path)` 这样一行代码——看起来很自然，很有信心。问题是：pandas 这个库根本没有这个函数。

一种可能的解释是：`read_csv`、`read_json`、`read_excel` 都是常见写法，模型顺着相似模式生成了 `read_yaml`。**名字像真的，不等于接口真的存在。**

从编造事实到业务逻辑出错，常见问题有三副面孔，发现难度与后果各不相同：

| 面孔 | 长什么样 | 发现难度与风险 |
|---|---|---|
| **编造 API** | 调用一个不存在的函数或参数 | 较易发现——编译检查或运行到相关路径时往往会报错 |
| **编造依赖** | 安装一个名字几乎正确、其实不存在的包 | 安装可能失败，也有专门的攻击方式盯着它（见第 12 章） |
| **隐蔽的业务／语义错误** | 代码能跑，但业务规则、接口衔接或边界处理是错的 | **往往更难发现——未覆盖相关场景的检查可能放过它** |

第三类尤其麻烦。它未必"编了一个东西"，也可能只是把真实需求理解错了。这种错误可能通过编译、现有测试与评审，一直活到生产环境里某个边界条件被触发的那一天。**这是错误类型，不等于"校准失效"。**

**对付这些问题没有一招制胜，可以先用三层组合：**

1. **接地**——把真实的上下文喂给它（项目文档、现有代码、报错日志）。让它"看着资料说话"。
2. **验证**——假设每一个 API 调用都可能是编的，用编译器和测试去机械化地验证，业务语义还要对照需求检查。这是第 9 章的内容。
3. **校准**——检查模型表达的置信程度与实际正确率是否匹配；不匹配才叫校准失效。**不能凭语气谦虚就选型，要在有代表性的任务上验证它说得多有把握、实际答得多准。**

> **一句话讲明白**：不妨把模型当成一个**读过很多资料、却未必掌握你项目细节的实习生**。给他资料，也要验收；他可能说得很自信，也可能表示不确定，**两种语气都不能替代检查**。

## 2.3 同一个问题问两遍，为什么答案不一样

这不是模型"不稳定"，而是有几个旋钮在被拧动。

**旋钮一：随机性。** 上一节说了，模型是"按概率挑一个词"。挑的时候带多少随机性，由一个参数控制。这个值调低，它几乎总挑概率最高的那个，输出稳定但死板；调高，低概率的词也有机会被选中，输出多样但更容易跑偏。

写代码时，低随机性通常是一个可测试的起点；但工具是否开放这个参数、默认值是什么，要看具体配置。

**旋钮二：思考多少。** 一些推理模型允许设置思考预算，影响回答前投入的计算。并不是所有模型都开放这个参数，也不能假定系统总会按任务难度分配得恰到好处。

这里有个很实际的坑：**默认档不一定适合你的任务。**要核对它用了多少推理计算、怎样计费，而不是只数你看得见的输出。

**旋钮三：采样与并发。** 即使参数完全一样，不同平台、不同并发条件下也可能出现差异。所以"我昨天用同样的提示词能得到正确结果"**不是一个可以依赖的假设**。想要可复现，得显式设计，而不是默认它成立。

> **核心判断 1**<br>
> 给智能体配模型时，**先核对默认值，不要照单全收**。<br>
> 在参数可调时，可以从"高难度重构：低随机 + 较多思考；批量模板：低随机 + 较少思考"开始试，再用任务结果决定。<br>
> **随机性影响输出稳定性，思考预算影响质量与成本；两者都不保证正确或完全可复现。**

## 2.4 它能"看见"多少

> **定义 · 上下文窗口（context window）**<br>
> 模型一次能"看见"的上下文长度上限，以 token 计。可以把它比作**工作台**：窗口里的内容会互相影响；窗口外的项目资料不会自动成为这次回答的依据，需要重新提供或通过工具取回。

2026 年，已有前沿模型提供百万 token 级窗口。一个中等规模的代码仓库塞进一次对话，在一些配置下已经可行。

但有三条常识必须说清楚，否则"大窗口"会变成一种幻觉。

**第一，窗口大不等于记性好。** 2023 年有一篇很有名的论文叫《Lost in the Middle》（Liu et al., TACL 2023, https://arxiv.org/abs/2307.03172 ）。它发现：把关键信息放在长文本的**开头或结尾**，模型找得最准；放在**中间**，准确率明显下降——即使是对那些专门为长上下文设计的模型。这个问题在 2026 年被大幅缓解，但没有消失。**把关键约束放在上下文的开头或结尾，仍然是个值得养成的习惯。**

**第二，注意力是稀缺的。** 你往窗口里塞五万行无关代码，模型对你真正关心的那两千行的专注就会被稀释。第 11 章会把这件事讲透——一句话先记住：**要给模型一张干净的工作台，而不是一间堆满杂物的仓库。**

**第三，窗口会满，满了要处理——而"怎么处理"是今天的核心工程决策。** 平台普遍的做法是自动压缩：把旧历史摘要化。**但压缩是有损的**，被摘要掉的细节，可能恰好是后面需要的那一条。

还有一种被命名的失败模式值得单独说：**上下文焦虑**。模型接近上下文上限时，可能**提前收尾**——把没干完的活包装成"已完成"交给你。这是长任务里值得检查的一种失败模式，不是每个模型必然出现的行为。

> **一句话讲明白**：上下文窗口像一张桌子。桌面再大，你也不该把整个仓库的书都摊上去——该摊的是**这一件事需要的那几本**。

**本章小结**

- 常见的自回归模型逐个预测 token 来生成文字，**流畅不等于事实正确**。训练、后训练、推理计算、上下文与工具共同影响能力，不能从生成机制推出全部本领与局限。
- 编造 API、编造依赖、**隐蔽的业务／语义错误**，发现难度与后果各不相同；最后一类不等于校准失效。
- 可以用**接地、验证、校准**组合应对。校准看的是置信程度与实际正确率是否匹配，不是语气是否谦虚，要用代表性任务检验。
- 随机性、思考预算、采样与并发条件都可能影响输出。**先核对默认值，不要照单全收。**
- 上下文窗口再大也不等于记性好：**中间可能漏、无关信息可能干扰、压缩可能丢细节**。还要留意"上下文焦虑"这类提前收尾的失败模式。

**对不写代码的人意味着什么**

你不需要懂 token，也能拿到两条：<br>
**第一，"AI 说得很有信心"和"AI 说得对"是两回事**——自信或谦虚都不能替代实际验证。<br>
**第二，"我给它看了所有资料"不等于"它读懂了所有资料"**——给得太多，反而可能让它漏掉关键的那一页。所以重要的约束，要放在最前面或最后面，并且反复确认。

**行动清单**

1. **检查你的模型参数**：核对随机性、思考预算等参数是否可调、默认是什么；对能调的参数显式记录配置，再比较不同设置的质量与成本。
2. **给每个重要输出配一个验证动作**：哪怕只是"这个函数真的存在吗"——查一次文档，或者直接跑一遍。选模型时，再用一组代表性任务检查答案正确率与它表达的置信程度是否匹配，别只看语气。
3. **控制你的上下文**：给智能体的每个任务，只放这件事需要的资料，别把整个仓库倒进去。关键约束写在最前或最后。
4. **留意"提前收尾"**：如果它说"已完成"，随机挑两条它声称做完的事**实际验一遍**。这个动作能帮你发现遗漏。
